## Purpose

定义收到 ntfy 消息后向 Windows 原生通知的转换和提交结果，保证纯文本安全展示、可诊断的系统抑制与失败处理，并限制点击激活不会触发消息携带的业务操作。

## ADDED Requirements

### Requirement: 原生通知初始化
系统 SHALL 使用 Windows 原生应用通知，注册固定名称 NtfyTray 和本地图标，在注册前准备点击激活处理并检查 API 可用性及通知设置；不使用自定义弹窗、消息框或托盘气泡替代。普通退出仅清理运行资源。

#### Scenario: 本地测试通知
- **WHEN** 普通用户从托盘选择测试系统通知且环境允许通知
- **THEN** 通过与业务通知相同的原生路径提交，不依赖 ntfy 网络

#### Scenario: 通知不可用
- **WHEN** API 初始化失败或系统禁止应用通知
- **THEN** 记录原因并反映通知异常或受限状态，不宣称用户已看到通知

### Requirement: 安全文本映射
系统 SHALL 将非空白 title 用作标题，否则使用 default_title；message 作为纯文本正文，include_topic 为 true 时附加来源 Topic。标题上限 128、正文上限 1024 个字符（含省略标记及来源），超出截断且不破坏 Unicode 字符；支持中文、换行和 XML 特殊字符。priority 不映射持续响铃，tags 不做复杂转换，click/actions/attachment 不执行、不下载、不打开。

#### Scenario: 回退及特殊文本
- **WHEN** 标题为空白且正文包含中文、换行、尖括号和超长内容
- **THEN** 使用默认标题，正文安全按纯文本显示并在项目长度限制内截断

#### Scenario: 消息携带动作
- **WHEN** 消息含 URL、HTTP 动作、命令或附件
- **THEN** 仅提交文本，不发起附加请求或执行动作

### Requirement: 明确通知结果与有限重试
系统 SHALL 在通知关闭时继续接收消息并记录 Suppressed；提交成功记录 Submitted；提交异常最多总计尝试三次，仍失败记录 Dropped 并显示异常，不无限阻塞后续消息。重试可取消，Windows 展示或阅读不作为提交成功的含义。

#### Scenario: 配置关闭通知
- **WHEN** notification.enabled 为 false
- **THEN** 继续订阅但不提交 Windows 通知，处理结果为 Suppressed

#### Scenario: 持续提交异常
- **WHEN** 三次提交均失败
- **THEN** 记录 Dropped 后允许后续消息处理；仅此时该消息可推进处理游标

### Requirement: 通知故障恢复条件
系统 SHALL 在初始化后、每条消息处理及手动测试通知时复查可检测的应用通知设置，不增加轮询任务。设置允许时仅清除设置受限故障；后续业务或测试通知获得 Submitted 时仅清除提交故障，Suppressed 不作为提交恢复证据。手动测试使用同一服务并遵守 notification.enabled；主动关闭通知不产生故障，也不冒充成功提交。初始化失败在本进程保持故障，重启且初始化成功后清除，不实现后台重复初始化。无法检测的横幅或专注设置不推断为组件故障。

#### Scenario: 系统设置恢复
- **WHEN** 用户重新允许应用通知后，下一条消息或手动测试触发设置复查
- **THEN** 清除设置受限故障并按当前配置处理；未触发复查前保留上次观测状态，不清除尚未恢复的提交故障

#### Scenario: 提交故障恢复
- **WHEN** 之前提交失败，后续业务或测试通知获得 Submitted
- **THEN** 清除通知提交故障，但保留其他来源尚未恢复的故障；配置关闭或系统抑制产生的 Suppressed 不清除提交故障

#### Scenario: 初始化故障恢复
- **WHEN** 通知初始化失败后用户重启应用
- **THEN** 仅在新进程初始化成功后清除该故障；失败时继续通过托盘及可用日志提示

### Requirement: 无业务操作的激活
系统 SHALL 保留必要通知激活处理但不打开业务窗口、消息 URL 或附件、不执行命令。旧通知在进程退出后激活时允许恢复托盘运行，仍遵守单主接收实例。

#### Scenario: 点击新旧通知
- **WHEN** 用户在程序运行中或退出后点击通知
- **THEN** 不执行消息动作且不产生第二套订阅；退出后被激活按新会话处理
