## Purpose

定义 NtfyTray V1 在目标 Windows 环境的交付形态和验收证据，区分开发机可运行与用户机器可部署，确保运行库先决条件、兼容性和长期接收能力都有可追溯验证。

## ADDED Requirements

### Requirement: 可复现的 Windows 发布
系统 SHALL 交付普通权限运行的 Windows x64 文件夹 ZIP，仅随包提供应用必需依赖、图标、示例配置及说明，不包含 .NET/Windows App Runtime 框架、未使用 SDK 组件、语言卫星资源和调试符号，不启用单文件和裁剪；依赖须锁定稳定版本，不使用浮动、Preview 或 Experimental 版本，不覆盖用户真实 config.yaml。

#### Scenario: 发布更新
- **WHEN** 生成发行包并按说明更新现有安装
- **THEN** 用户配置保留，发行包不携带真实 Token，并可从锁定依赖复现构建

### Requirement: 运行库说明与用户部署验收
发行说明 SHALL 明确 .NET 10 Desktop Runtime x64 和匹配 Windows App SDK 稳定运行库版本、安装及检查方法和本地通知验证步骤，不承诺底层运行库缺失时仍显示托盘。按用户 2026-09-11 的明确安排，代理不执行无开发工具的干净 Windows 测试；最终部署由用户验收，不作为本轮代码与候选包交付的前置条件。代理须提供候选清单、说明及已验证范围，不将开发机证据表述为干净系统实测通过。

#### Scenario: 用户部署验收交接
- **WHEN** 用户按发行说明准备环境并解压运行
- **THEN** 按说明检查托盘、原生测试通知及通知激活，由用户决定最终验收；代理记录交接状态和已验证环境，不虚构未执行的部署结果

### Requirement: 实际服务链路验收
系统 SHALL 通过真实 ntfy 和正式 Tunnel 固定域名测试 SSE 实时转发、认证、断网、服务器/Tunnel 重启、缓存补收和睡眠恢复；不依赖浏览器运行、临时 Quick Tunnel、客户端 cloudflared 或交互式代理登录。

游标拒绝、有效响应截断和 HTML 异常响应等难以安全、稳定触发的诊断分支，可采用有来源依据的脱敏响应夹具验证客户端行为；验收记录 SHALL 区分实际服务已验证内容、夹具覆盖内容及限制。夹具须来自真实脱敏响应或明确协议依据，不将自行猜测的错误载荷作为分类依据；上述真实主链不得用夹具替代。

#### Scenario: 实际域名接收
- **WHEN** Chrome 完全退出后通过部署域名发送消息
- **THEN** 客户端实时接收且无需等连接结束才取得事件，标题正文和 Topic 映射正确

#### Scenario: 罕见诊断分支无法实服复现
- **WHEN** 目标服务无法安全、稳定触发游标拒绝、有效截断或 HTML 异常响应
- **THEN** 用可信夹具验证对应客户端分支并记录来源、目标服务版本和实服未验证范围；实际主链通过且这些分支验证通过后可完成链路验收，不宣称已在实服复现，也不把缺少截断提示当作缓存完整

### Requirement: 性能与长期稳定性证据
系统 SHALL 在正常负载下达到完整消息取得至通知 API 调用延迟 P95 不超过一秒；首次正式交付前须有一次连续运行 24 小时无异常退出、内存/线程/句柄持续异常增长的通过记录。记录负载、采样方式和结果，不将网络传输或 Windows 横幅调度时间计入该延迟。性能验证可合并于一次正常联调或稳定性运行，使用一台目标机器的一组有限样本，不以单条消息代替统计，不要求独立性能平台或多机多轮压测。后续候选变化按本规格的影响范围规则决定重测与证据复用。

#### Scenario: 长期与延迟测试
- **WHEN** 执行规定负载和 24 小时实机测试
- **THEN** 留存延迟统计与资源趋势；首次未执行或失败明确标记，不以部分测试通过宣称 V1 完成；后续复用须关联已通过记录并说明适用依据

### Requirement: 完整交付证据
V1 SHALL 交付源码、锁定依赖、示例 YAML、ZIP、运行库说明、使用排错文档及自动化和实机验收记录，覆盖配置、消息、SSE 分块、格式、去重、重连、取消、多 Topic 隔离和日志脱敏。

每个行为须有适当验证依据；同类边界可用参数化测试覆盖，第三方能力可用配置核查和必要接入测试验证，不要求每个场景同时具备单元、集成和实机测试。涉及真实平台或服务的必要验收仍须实测，已有有效证据可被多个任务引用。

#### Scenario: 交付审查
- **WHEN** 判定整个 V1 实施完成
- **THEN** 所有任务与规格验收有对应证据，缺少关键实机验证时不得标记整体完成

### Requirement: 验收与候选发布包一致
系统 SHALL 在完整自动化测试通过后、V1 实机集成和首次 24 小时验收前生成包含运行说明的候选 ZIP，将源码基线、锁文件、发布命令、ZIP SHA-256、解压文件清单及运行文件指纹集中记录于一份候选清单；验收配置和环境集中记录并脱敏。各项验收核对并引用这些记录，不重复抄录整套字段。实机部署、更新回退、服务联调、延迟和长期测试使用已标识的候选包。候选变化时按下述规则分析差异及证据适用范围；所有必要验收通过或有依据复用后，直接交付最终候选 ZIP，不为发行重新构建。T0 的最小路线验证不替代候选包验收。

#### Scenario: 同一候选包完成验收
- **WHEN** 最终候选 ZIP 及运行内容与候选清单一致，必要验收已通过或有明确依据复用
- **THEN** 直接交付该 ZIP 并关联验证记录，不为发行重新生成二进制文件

#### Scenario: 验收后候选内容变化
- **WHEN** 源码、依赖、发布选项或包内文件变化
- **THEN** 更新候选清单，记录变更内容、影响判断和补测结果；影响连接循环、并发调度、资源获取/释放、长期资源占用或相关依赖及发布配置时，须对新候选重新执行完整 24 小时验收，影响不能确定时同样重跑。与上述方面无关且有可追溯审查依据时，可关联既有通过记录，补做受影响自动化及必要实机检查后复用长期证据；仅文档变化且运行内容未变时核验包内容即可。首次未通过、既有失败或已失效记录不得作为复用依据，不宣称未实际运行的新候选已实测 24 小时
