## Purpose

定义每个 Topic 的实时接收、故障隔离与运行期间恢复行为，在有限内存和服务端缓存范围内尽力处理消息，同时明确认证、传输安全、顺序和历史补收的边界。

## ADDED Requirements

### Requirement: 独立安全的 SSE 订阅
系统 SHALL 为每个 Topic 建立一条 HTTPS SSE 订阅，请求 /<topic>/sse 并声明 Accept: text/event-stream；仅发送配置 Token 的认证头，执行正常 TLS 校验且拒绝非预期重定向，不跟随消息 URL。一个 Topic 故障不得停止其他 Topic。

#### Scenario: 返回登录页面
- **WHEN** 端点重定向或返回 HTTP 200 HTML 而非 text/event-stream
- **THEN** 报代理或认证配置错误，不解析为 SSE，不向重定向目标转发凭据

#### Scenario: 单 Topic 权限失败
- **WHEN** 一个 Topic 返回 403 而另一个合法
- **THEN** 后者持续接收，前者独立呈现错误和重试

### Requirement: 完整事件解析和业务过滤
系统 SHALL 按完整 SSE 事件解析 JSON，容忍分块读取和额外 JSON 字段，按 JSON event 分流；open、keepalive 仅更新连接活跃状态，message 校验 ID、Topic、内容后处理，未知事件忽略业务内容，坏 JSON 或无效消息跳过并记录安全诊断。

#### Scenario: 网络分块
- **WHEN** 一个事件跨多次读取、中文跨字节分块或一次读取包含多个事件
- **THEN** 得到正确完整消息，不以字节块作为 JSON 边界

#### Scenario: 非消息和无效内容
- **WHEN** 收到含 ID 的 open、keepalive、未知事件、坏 JSON 或缺失必要字段的 message
- **THEN** 不产生业务通知；无效事件不使进程崩溃，额外字段不导致合法消息被拒绝

### Requirement: 连接确认及空闲超时
系统 SHALL 在响应类型正确且收到有效 ntfy 事件后才标为已连接；默认响应头预算 15 秒，取得响应头后解除该阶段计时，长连接无固定总时限，连续 150 秒无有效事件时重建连接。

#### Scenario: 长期仅心跳
- **WHEN** 合法心跳持续到达但没有业务消息
- **THEN** 连接保持健康且不因连接总时长或无业务消息而重连

#### Scenario: 连接假死
- **WHEN** 连续超过配置空闲阈值没有有效事件
- **THEN** 取消旧连接并进入重连；坏 JSON 不刷新有效事件时间

### Requirement: 分类重连
系统 SHALL 对 DNS、连接超时、断网、EOF 和 HTTP 500/502/503/504 指数退避重试，默认基准 1、2、4、8、16、30 秒并加 ±20% 扰动；从首个有效 ntfy 事件进入 Connected 起持续稳定满 60 秒才重置。429 优先遵守有效 Retry-After 并允许超过普通上限；401/403 每 300 秒低频重试；404、明显错误地址及代理配置错误等待修改后重启。证书错误不得绕过校验。断线恢复仅更新托盘和日志。

#### Scenario: 短连接反复失败
- **WHEN** 多次取得 HTTP 200 后立即断开
- **THEN** 不重置失败计数，退避增长至基准上限

#### Scenario: 服务端限流
- **WHEN** 429 提供有效 Retry-After 且超过 30 秒
- **THEN** 不早于该等待时间重试；缺失或无效时使用普通退避

#### Scenario: 主动停止
- **WHEN** 用户退出触发取消
- **THEN** 正常停止，不记录为网络故障，不启动下一次重连

### Requirement: 恢复信号不产生重复订阅
系统 SHALL 在睡眠恢复或网络变化时通过现有订阅循环请求重建连接，旧连接终止后才创建新连接，每个 Topic 最多一条活动订阅。恢复信号不得缩短当前重试等待（包括普通退避、429 Retry-After 及 401/403 的 300 秒等待），不得重新激活等待修改配置后重启的订阅；等待按已过去的时间计算，信号不得重新起算等待。主动退出优先于所有恢复信号与等待。

#### Scenario: 连续恢复信号
- **WHEN** 睡眠恢复和网络变化信号连续到达
- **THEN** 合并恢复请求，不叠加订阅循环或并存活动连接

#### Scenario: 等待期间收到恢复信号
- **WHEN** 普通退避、429 限流或 401/403 权限等待期间收到睡眠恢复或网络变化信号
- **THEN** 仍遵守原等待截止时间，到期后至多开始一次连接；若睡眠期间等待已到期则可重试，不重新起算等待

#### Scenario: 配置故障及退出期间收到恢复信号
- **WHEN** 订阅因 404 或代理配置错误等待重启，或程序已开始退出时收到恢复信号
- **THEN** 不建立新连接；永久配置故障保留至重启，退出可立即取消等待

### Requirement: 会话内缓存补收
系统 SHALL 仅在内存保存每 Topic 最后处理完成消息 ID 和必要服务器时间；新进程首次订阅不主动取历史。运行中重连优先使用消息 ID 的 since；尚无业务消息但已有有效连接时使用首次有效连接事件服务器时间，不使用 open/keepalive ID。无效游标必须有界回退，缓存截断须记录可能未恢复消息。

#### Scenario: 同进程断线
- **WHEN** 运行期间断线后恢复且服务器缓存有效
- **THEN** 按内存恢复位置尝试补收断线消息

#### Scenario: 没有业务游标
- **WHEN** 成功连接后尚未处理业务消息即断线
- **THEN** 使用可用的首次连接服务器时间恢复；无可用参考时仅实时重连

#### Scenario: 程序重新启动
- **WHEN** 用户退出或电脑重启后启动新进程
- **THEN** 不读取持久游标且不主动补收退出期间消息

#### Scenario: 恢复位置被拒绝
- **WHEN** 服务端响应被明确识别为拒绝已失效恢复位置
- **THEN** 有界回退且记录可能丢失，不无限重复同一错误请求，不承诺恢复不存在的消息；普通 400、断线或没有新消息不单独作为游标失效证据

#### Scenario: 有效响应中的缓存截断
- **WHEN** 成功 SSE 响应携带 X-Messages-Truncated: 1
- **THEN** 记录可能有消息未恢复，继续按正常顺序处理返回的缓存消息及后续实时事件；不因截断取消有效连接、重置 since 或触发游标回退，游标仍仅在消息处理完成后推进

### Requirement: 有界去重与处理顺序
系统 SHALL 每 Topic 按到达顺序处理，以最近 2048 个已处理消息 ID 去重并淘汰最旧项；不同 Topic 不承诺全局顺序。仅获得 Submitted、Suppressed 或已记录的 Dropped 结果后标记处理完成并推进游标，不使用无界工作队列。

#### Scenario: 重复与同文消息
- **WHEN** 相同 ID 在保留集合内重复到达或同文不同 ID 到达
- **THEN** 前者不重复提交，后者分别正常处理；集合不超过 2048 项

#### Scenario: 提交未完成
- **WHEN** 消息已接收但尚无明确处理结果
- **THEN** 不推进恢复位置，不承诺严格一次送达或用户已阅读
